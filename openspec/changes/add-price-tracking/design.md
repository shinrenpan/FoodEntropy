## Context

價格欄位本身是最簡單的部分：一個 optional 的數值，符合既有的 CloudKit-safe 約束。真正的設計工作在於**這個數字要在什麼時候、對誰說話**——決定已記錄於 proposal（前瞻為主、回顧為附屬）。

本文件記錄實作面的決定，其中兩項是容易照抄既有慣例而抄錯的地方。

## Goals / Non-Goals

**Goals:**
- 記錄價格在食材離開清單時**不得**被清除，及其與圖片處理的差異。
- 記錄前瞻金額的取樣範圍與「至少」語氣的必要性。
- 記錄輸入與顯示的格式化歸屬。

**Non-Goals:**
- 不重述 proposal 已定的呈現方向。
- 不新增已處理食材的編輯入口。
- 不做預算、目標或趨勢。

## Decisions

### 解析食材時清除圖片，但**保留**價格

`persistence` 目前在標記已使用／丟棄時會把 `imageData` 設為 `nil`，理由是歷史紀錄不需要照片、而照片是唯一體積大的資料。**價格不適用這個處理**：回顧金額正是以已解析食材的價格計算，清除它等同讓該功能永遠取不到資料。

這是本 change 最容易出錯的一點——實作時若照著相鄰的 `imageData = nil` 一併處理價格，功能會靜默失效：畫面顯示「已丟棄 NT$0」，而測試若只驗證「標記後離開清單」不會發現。價格是數值，體積可忽略，沒有任何清除的理由。

### 前瞻金額只取 `nearExpiry` 桶，不含 `expired` 與 `fresh`

金額取自 active 且 `expiryStatus` 為 `nearExpiry`（0–3 天）的食材中已記錄價格者。

不含 `fresh` 的理由：「你冰箱裡有 NT$1,200 的食物」沒有行動含義——那是正常的庫存，不是風險。

不含 `expired` 的理由：已過期的食材不再屬於「即將到期」，把它算進同一個數字會讓語意混淆——使用者無法分辨這筆錢是還救得回來，還是已經沒救了。若未來要呈現已過期的金額，那是另一種訊息（「已經浪費掉但還沒處理」），應另行設計，不與前瞻金額混用。

### 一律以「至少」語氣呈現，而非條件式

金額文案固定使用「至少」，不因涵蓋率高低而切換。理由：涵蓋率是浮動的，使用者每新增一項未填價格的食材就會改變；若文案在「NT$300」與「至少 NT$300」之間跳動，反而顯得系統在隱瞞什麼。固定用「至少」讓陳述永遠為真，且不需要在畫面上解釋涵蓋率。

當所有 `nearExpiry` 食材皆有價格時，「至少」仍然成立，只是保守——這個代價遠小於顯示一個會被誤讀為完整的數字。

### 沒有可計算的金額時整行不渲染，而非顯示零或引導

`nearExpiry` 桶中沒有任何食材帶價格時（含桶本身為空），該行完全不出現。不顯示「NT$0」——那會被讀成「沒有損失風險」，與事實無關；也不放「記錄價格以查看金額」的引導——首頁版面已相當擁擠（廣告位、環形圖、浪費統計、三個桶、新增按鈕），在尚未驗證價值的功能上先佔位置並不划算。

### 輸入不帶符號，顯示交由系統格式化

輸入欄位只收數值，使用數字鍵盤並允許小數；貨幣符號由顯示端依裝置 locale 產生，使用者不輸入也不選擇幣別。理由：`localization` 已規範「金額與日期交由系統格式化，不自行組字串」——手工組貨幣字串必然在某個地區出錯，而錯誤只有該地區的使用者看得到。

允許小數而非限定整數：本 app 全球發行，台幣情境用不到小數，但美元等幣別需要。

### 價格為「這筆記錄的總花費」

無數量欄位，一筆記錄即一次採購，因此 `price` 代表該筆的總花費而非單價。介面上不附加說明文字——Form 是使用者自行操作的頁面，本 app 的既有取向是保持簡單。此語意需在規格中明確，因為它決定了彙總結果的意義。

## Implementation Contract

**Behavior (observable):**
- Form 的購買日期同一區塊出現選填的價格欄位；留空可正常儲存。
- 點擊價格欄位跳出數字鍵盤，可輸入小數。
- 已輸入的價格在畫面上以裝置地區的貨幣格式顯示。
- 首頁在有 `nearExpiry` 食材帶價格時，顯示「至少 <金額>」的即將到期金額；沒有時該行不出現。
- 補填某項 `nearExpiry` 食材的價格後返回首頁，金額隨即增加。
- 標記某項食材為已使用或丟棄後，其價格仍保留於紀錄中，並計入浪費統計區的已丟棄金額。
- 浪費統計區的已丟棄金額為附屬呈現，浪費率百分比仍為該區主要資訊。

**Interface / data shape:**
- `FoodItemEntity.price: Double?`，無預設值即為 optional，符合 CloudKit-safe。
- `FoodItem.price: Double?`，經 `toDomain()` 帶出。
- `SwiftDataManager.create(...)` 與 `update(...)` 新增 `price: Double?` 參數。
- `resolve(id:to:)` **不得**修改 `price`。
- `FoodFormViewModel.State` 新增價格欄位；不納入 `isSaveEnabled` 的判斷；納入 dirty 比對的 `Snapshot`。
- `HomeViewModel.State` 新增前瞻金額與已丟棄金額兩個彙總值。

**Acceptance criteria:**
- `grep -n "price" Sources/Core/Persistence/SwiftDataManager.swift` 顯示 `resolve` 路徑未觸及該欄位。
- 名稱有效但價格留空時，儲存按鈕維持啟用。
- 僅修改價格欄位時，返回會觸發放棄確認（表示 `Snapshot` 已納入該欄位）。
- 前瞻金額的計算來源僅含 `expiryStatus` 為 `nearExpiry` 且 `price` 非 nil 的 active 食材。
- 程式碼中無自行組成的貨幣字串（無硬編符號、無 `NumberFormatter` 手工設定貨幣）。

**Scope boundaries:**
- In scope：價格欄位的持久化與轉換、Form 輸入、首頁前瞻金額、浪費統計區的附屬金額。
- Out of scope：已處理食材的編輯入口、預算與目標、趨勢圖、已過期食材的金額呈現、Widget 的金額顯示（屬 `add-widget`）。

## Risks / Trade-offs

- [涵蓋率低時金額偏小] → 「至少」讓陳述為真，但提醒力道仍隨涵蓋率下降。這是選填設計的必然代價；強制填寫會讓使用者連食材都懶得記錄，損失更大。
- [價格必須在食材離開清單前填寫] → 已處理食材無編輯入口，事後想補也補不了。前瞻主軸不受影響（只看 active），但回顧金額的涵蓋率會長期偏低。
- [新增欄位需重新部署 CloudKit Production schema] → 屬 additive 因而安全，但部署後不可回頭；欄位名稱與型別一旦上線就固定（見 `persistence` 的「schema 只加不改」）。
- [前瞻金額只算 `nearExpiry`] → 使用者若期待看到「冰箱總值」會落空。這是刻意的——總值沒有行動含義——但可能需要在測試後重新評估。
- [未驗證的假設：前瞻比回顧更能促成行動] → 本設計建立在此假設上，尚未經真實使用者驗證。proposal 已註明測試後可能調整方向。
