## Context

App Store Connect 上的商店資訊不在版控裡，卻直接影響 app 的實際行為：行銷 URL 決定廣告驗證能否成立、隱私標籤決定審核能否通過、文案決定使用者的期待。它是唯一一個「規格在 repo 裡、規範對象在 repo 外」的 capability。

因此本 capability 刻意**不**在 repo 中保留線上值的抄本——抄本會漂移，而漂移的抄本比沒有抄本更危險（讓人以為查過了）。線上實際值一律以 App Store Connect API 查詢為準；本規格只規範「這些欄位之間必須維持什麼關係」。

## Goals / Non-Goals

**Goals:**
- 記錄行銷 URL 與 app-ads.txt 託管網域的一致性要求，以及缺漏時的實際症狀。
- 記錄隱私權政策 URL 必須與 app 內連結同一。
- 記錄文案不得承諾 build 沒有的功能。
- 記錄隱私標籤必須涵蓋廣告 SDK 的收集項。
- 記錄發行區域排除的合規前提。
- 記錄哪些欄位可即時修正、哪些必須綁版本送審。

**Non-Goals:**
- 無行為變更。
- 不涵蓋 app-ads.txt 檔案本身（`advertising`）、IAP 商品設定、截圖製作流程。
- 不在 repo 保留線上值抄本。

## Decisions

### 行銷 URL 必填，且其 hostname 必須等於 app-ads.txt 的託管網域

這是本 capability 最重要的一條。廣告網路的爬蟲不從 app 取得任何資訊，而是從商店資訊的行銷 URL 解析出 hostname，再到 `https://<hostname>/app-ads.txt` 尋找檔案。因此驗證需要三者同時成立：檔案已發布且可公開存取、行銷 URL 已填寫、兩者的 hostname 相同。

v1.0.0 只滿足了第一項。實際症狀是後台顯示「找不到 app-ads.txt 檔案」，且「app-ads.txt 網址」與「上次檢索時間」兩欄都是空的——空的檢索網址正是「爬蟲推導不出網域」的訊號，而非「去過但沒找到」。這個區別很重要：錯誤訊息把人導向檢查檔案，但檔案從頭到尾都是對的。

未驗證的後果是部分廣告需求方不出價，填充率與收益受損。

### 隱私權政策 URL 與 app 內設定列連到的是同一個

app 內「隱私權政策」開啟的 URL 與填入 App Store Connect 的必須相同。理由：兩者若分歧，使用者在 app 內看到的政策與商店頁面聲明的政策不一致，這在審核與合規上都站不住腳。app 內的那個 URL 是型別層級常數（見 `settings-ui`），是唯一的來源。

### 商店文案不得承諾 build 沒有的功能

描述、宣傳文字、關鍵字與截圖都不得呈現目前版本沒有的能力。理由：這是明確的退件原因，且比功能缺陷更難補救——審核者看到的是「你說有但我找不到」。對本 app 而言特別要注意的是 roadmap 上的項目（如 Widget、Siri 整合）在實作完成前不能出現在文案中。

### 隱私標籤必須涵蓋廣告 SDK 實際收集的資料

隱私標籤不只涵蓋 app 自己收集的資料，也要涵蓋所接第三方 SDK 收集的。本 app 不收集任何使用者資料（食材紀錄留在裝置與使用者自己的 iCloud），但 AdMob 會收集裝置識別資訊用於第三方廣告。理由：漏報 SDK 的收集項是常見的退件與事後更正原因，而且它不是「app 有沒有做」的問題，是「你接的 SDK 有沒有做」的問題。

### 發行區域的排除是合規決定，不是市場偏好

排除歐盟是為了避開 GDPR 與 DSA 的額外合規負擔（並因此可以不接 UMP 同意流程，見 `advertising`）；排除其他特定地區亦各有其法規理由。理由：這些排除看起來像是可以隨手調整的市場設定，實際上每一項都綁著一組尚未完成的合規工作。要新增地區，必須先完成對應的合規前置，而不是只改一個開關。

### 分辨可即時修正與需送審的欄位

支援 URL、宣傳文字與隱私權政策 URL 這類欄位可在已上架版本上隨時更新；行銷 URL、描述、關鍵字與截圖則綁定版本，必須隨新版本送審。實測 v1.0.0 上架後嘗試以 API 補填行銷 URL，得到 `409 STATE_ERROR — Attribute 'marketingUrl' cannot be edited at this time`。

理由與用法：會隨時間漂移的內容（例如提及具體數字、時效性資訊）應盡量放在可即時修正的欄位，否則一個小錯字就要為它送一次審。反過來說，需送審的欄位在送審前必須逐一檢查，因為修正成本是以「天」計。

## Implementation Contract

**Behavior (observable):**
- 商店頁面顯示「開發者網站」連結，其網域與 app-ads.txt 的託管網域相同。
- 廣告網路後台的 app-ads.txt 狀態顯示已檢索並通過驗證，且檢索網址非空。
- app 內設定的隱私權政策與商店頁面的隱私權政策連到同一頁。
- 商店文案描述的每一項能力都能在目前版本中找到。
- 隱私標籤列出廣告 SDK 收集的裝置識別資訊及其用途。

**Interface / data shape:**
- 線上實際值以 App Store Connect API 查詢為準，repo 內不保留抄本。
- 行銷 URL：必填，hostname 須等於 `advertising` 所述 app-ads.txt 的託管網域。
- 隱私權政策 URL：等於 `settings-ui` 中的型別層級常數。
- 欄位修正成本分類：可即時修正（支援 URL、宣傳文字、隱私權政策 URL）／需綁版本送審（行銷 URL、描述、關鍵字、截圖）。

**Acceptance criteria:**
- 以 API 查詢每個語系的行銷 URL，皆非空且 hostname 一致。
- 對該 hostname 根目錄請求 app-ads.txt 回傳成功且內容含本 app 的 publisher 條目。
- 以 API 查詢的隱私權政策 URL 與程式碼常數逐字相同。
- 送審前逐項比對描述所述功能與該 build 的實際功能。

**Scope boundaries:**
- In scope：行銷 URL 與網域一致性、隱私權政策同一性、文案與實作一致性、隱私標籤涵蓋範圍、發行區域合規前提、欄位修正成本分野。
- Out of scope：app-ads.txt 檔案本身（`advertising`）、IAP 商品設定與審核附註、截圖製作流程、線上值的抄本。

## Risks / Trade-offs

- [v1.0.0 的行銷 URL 目前為空] → app-ads.txt 持續處於未驗證狀態，收益受損。修正需隨新版本送審（`marketingUrl` 在已上架版本回 `409 STATE_ERROR`），無法單獨補填。此為已知未結項目。
- [規範對象不在 repo 內] → 沒有任何自動化能防止線上欄位被改壞；本規格只能在送審前的人工檢查中發揮作用。
- [不保留線上值抄本] → 每次要確認現況都得查一次 API，比讀 repo 慢。這是刻意的取捨——抄本漂移後會給出錯誤的信心。
- [隱私標籤依賴對第三方 SDK 行為的理解] → SDK 版本更新可能改變其收集項，而 app 這一側不會有任何訊號。升級廣告 SDK 時需一併重新確認隱私標籤。
- [發行區域的合規理由未逐項記錄於此] → 本規格只記錄「排除是合規決定」的原則，各地區的具體法規要求需另行查證。
