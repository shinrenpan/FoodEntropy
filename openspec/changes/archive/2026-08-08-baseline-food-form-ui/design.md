## Context

新增與編輯是同一個畫面的兩種模式，差別只在初值與儲存時呼叫建立或更新。這個決定讓兩條路徑共用全部的驗證、照片處理與放棄確認邏輯——任何一邊的修正自動適用另一邊。

表單刻意只做欄位編輯：刪除、標記已使用、標記丟棄、延長效期都不在這裡，一律回首頁的 row 手勢處理。理由是這些操作改變的是食材的「狀態」而非「內容」，把它們混進編輯畫面會讓「儲存」的語意變得模糊——按下儲存到底是存欄位，還是也確認了剛才按的那個狀態變更？

## Goals / Non-Goals

**Goals:**
- 記錄雙模式共用單一畫面的分工。
- 記錄名稱驗證與儲存啟用條件。
- 記錄日期區間的兩道防線。
- 記錄未儲存變更的判定方式，與快照排除 UI-only 欄位的理由。
- 記錄自訂返回鈕取代系統返回鈕的理由。
- 記錄儲存流程的固定順序。

**Non-Goals:**
- 無行為變更。
- 不涵蓋 `persistence` 的壓縮與落地、`notification` 的排程規則、`navigation` 的導航機制、`home-ui` 的清單。

## Decisions

### 新增與編輯共用單一畫面，以模式區分

`FoodFormMode` 為 `add` 或 `edit(FoodItem)`。標題、初值與儲存行為依模式分流，其餘完全共用。理由：兩者的欄位、驗證、照片處理與放棄確認完全相同，拆成兩個畫面會讓每次修正都要做兩遍，且容易只改一邊。`edit` 攜帶 Domain Model 而非 id，因此初值不需要再查一次資料庫。

### 新增模式的到期日預設為三天後

`add` 模式初值為購買日今天、到期日今天加三天。理由：預設值的作用是讓多數情況少按幾下。三天恰好落在 `food-item` 的近期警示窗內，使用者若直接沿用預設，這筆食材一建立就在「3 天內到期」桶——這對生鮮是合理的起點，也讓使用者立刻看到分桶的意義。

### 名稱去除頭尾空白後非空才可儲存

儲存按鈕在名稱無效時停用，而非按下後才報錯。理由：停用讓「還不能存」在按下之前就可見，省掉一次無效互動與錯誤訊息。去空白比對則避免只輸入空白字元就能建立一筆無名食材——而 `persistence` 的 schema 為了 CloudKit 相容不能設必填約束，這道驗證是唯一的把關。實際寫入時也存去空白後的名稱，不只用於判斷。

### 日期區間有兩道防線

其一，到期日選擇器的可選範圍下限綁定當前購買日，使用者無法直接選一個比購買日早的到期日。其二，當購買日被改到晚於現有到期日時，把到期日一併推到該日。理由：只做第一道時，使用者可以先選好到期日、再把購買日改到更晚，繞出一個無效區間；只做第二道時，選擇器仍允許選出無效日期再被修正，體驗上像是「選了又被改掉」。兩道並用讓無效區間在任何操作順序下都不會出現。

### 未儲存變更以初始快照比對，快照排除 UI-only 欄位

ViewModel 在初始化時保存一份初始欄位的快照，判定是否有變更時以當前欄位重建快照與之比對。快照只含名稱、購買日、到期日、照片四項，不含 `showDiscardConfirm` 這類純顯示旗標。理由：若把顯示旗標納入比對，彈出確認框這個動作本身就會改變比對結果——使用者按下返回、確認框出現、狀態因此「變髒」，即使他什麼欄位都沒改。快照放在 ViewModel 而非 State，也是為了讓它不參與 State 的 `Equatable` 比較。

### 自訂返回鈕，隱藏系統返回鈕

畫面隱藏系統返回鈕，在同一位置放自己的「取消」。理由：系統返回鈕直接 pop，沒有任何攔截點可以插入「要放棄變更嗎」的詢問。自訂按鈕讓返回先經過 ViewModel，由它依是否有未儲存變更決定直接關閉或先確認。

### 照片以動作選單取得，移除項僅在已有照片時出現

點擊照片區塊彈出選單：拍照、從相簿選、移除照片（僅當已有照片）、取消。選取後立即壓縮並存入狀態（壓縮規格見 `persistence`）。有照片時在表單下方額外顯示大圖預覽。理由：選單把三種來源收在一次點擊之後，避免在表單上並排多個按鈕；移除項有條件出現，是因為對一個沒有照片的欄位提供「移除」沒有意義。大圖預覽則讓使用者確認拍到的內容，縮圖尺寸不足以判斷。

### 儲存流程的順序固定

按下儲存後依序：去空白取名稱、依模式寫入、請求通知權限（僅在尚未決定時實際彈窗）、以當前 active 清單對帳排程、關閉畫面。理由：權限請求必須在寫入之後——此時使用者已完成「記住這項食材」的動作，權限的用途最明確（見 `notification`）。對帳必須在寫入之後才能讀到新資料。關閉放在最後，讓首頁在重新出現時已能撈到最新結果。

### 本畫面不提供狀態變更操作

刪除、標記已使用、標記丟棄、延長效期都不在表單上。理由：這些改變的是食材狀態而非欄位內容，若放在此處，「儲存」的語意會變得模糊，且與首頁 row 的手勢重複。使用者要處理狀態時回首頁操作。

## Implementation Contract

**Behavior (observable):**
- 從首頁新增進入時標題為「新增食材」，購買日預設今天、到期日預設三天後、名稱為空、無照片。
- 從首頁點一列進入時標題為「編輯食材」，所有欄位帶入該食材現值。
- 名稱為空或只有空白時，儲存按鈕呈停用狀態。
- 到期日選擇器不允許選擇早於購買日的日期。
- 把購買日改到晚於現有到期日時，到期日隨之移到該日。
- 未修改任何欄位就按取消，直接返回首頁。
- 修改過任一欄位後按取消，先詢問是否放棄變更；選擇繼續編輯則留在表單且變更仍在。
- 點照片區塊出現拍照／從相簿選／取消；已有照片時另有移除照片。
- 選好照片後表單下方顯示大圖預覽。
- 儲存後返回首頁，首頁清單包含這次的新增或修改。
- 第一次儲存時出現通知權限詢問。
- 表單上沒有刪除、標記已使用、標記丟棄或延長效期的入口。

**Interface / data shape:**
- `FoodFormMode`：`add` / `edit(FoodItem)`。
- `FoodFormViewModel`：`@Observable @MainActor`；`doAction(_:)` 單一進入點；`navigationTitle` 依模式回傳在地化字串。
- `State`：`name`、`purchaseDate`、`expiryDate`、`imageData`、`showDiscardConfirm`；計算屬性 `isSaveEnabled`（名稱去空白後非空）。
- `ViewAction`：`purchaseDateChanged(Date)`、`imagePicked(Data?)`、`removeImage`、`saveDidTap`、`dismissDidTap`、`discardConfirmed`、`discardCancelled`。
- `Router`：`close`。
- `Snapshot`：private struct，僅含四個內容欄位，供 dirty 比對。
- HostController 於初始化時設定隱藏 tab bar。

**Acceptance criteria:**
- `Snapshot` 的欄位不含 `showDiscardConfirm`。
- 到期日選擇器的可選範圍以當前購買日為下限。
- `purchaseDateChanged` 在新購買日晚於現有到期日時同步更新到期日。
- `saveDidTap` 在儲存條件不成立時直接返回，不寫入。
- `save()` 內的順序為：寫入 → 請求權限 → 對帳排程。
- 表單畫面未使用系統返回鈕。
- 表單的 action 列舉中不含任何狀態變更（消耗／丟棄／刪除／延長）。

**Scope boundaries:**
- In scope：雙模式、欄位驗證、日期約束、dirty 判定與放棄確認、自訂返回鈕、照片取得與移除與預覽、儲存流程順序、不提供的操作。
- Out of scope：照片壓縮與落地（`persistence`）、通知排程與權限語意（`notification`）、push 與返回機制（`navigation`）、首頁清單（`home-ui`）、出口語意（`food-item`）。

## Risks / Trade-offs

- [互動式滑動返回可能繞過放棄確認] → 表單以 push 進入，而 `navigation` 的手勢條件允許預設 push 轉場使用邊緣滑動返回；此畫面雖隱藏了系統返回鈕，但手勢是否一併失效需實機確認。若手勢仍可用，使用者滑動返回時不會經過 ViewModel，未儲存變更將直接遺失而不詢問。**尚未實機驗證**，記錄於此以待查核。
- [沒有錯誤回饋的儲存失敗] → `persistence` 的寫入失敗在 Release 是靜默的，表單在儲存後一律關閉並回首頁。若寫入實際失敗，使用者會回到首頁卻找不到剛才那筆，且沒有任何錯誤訊息。
- [dirty 判定包含照片二進位資料] → 比對照片以 `Data` 相等進行，重新選擇同一張照片會因壓縮結果不同而被判定為有變更。實務影響輕微，但確實可能出現「我什麼都沒改」卻跳出確認的情況。
- [新增模式的三天預設是猜測] → 對保存期長的乾貨而言預設值偏短，使用者每次都要調整。目前沒有依食材類型或使用者習慣調整預設的機制。
