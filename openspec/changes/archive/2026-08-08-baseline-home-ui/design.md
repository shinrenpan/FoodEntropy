## Context

首頁原本規劃為兩個分頁：首頁（平鋪可操作）與分析（分桶唯讀總覽）。v1.0.0 開發過程中發現兩者的清單本質相同——分析頁只是把首頁的食材換個排法再列一次——因此合併為單頁：頂部放原分析頁的現況甜甜圈與浪費統計，下方的分桶清單改用可互動的 row。`AnalyticsView` / `AnalyticsViewModel` / `AnalyticsHostController` 已刪除。

合併後首頁同時承擔三個角色：現況一覽、歷史統計、日常操作。它是 app 中唯一會讓使用者動手的畫面。

## Goals / Non-Goals

**Goals:**
- 記錄單頁合併的沿革與理由。
- 記錄三桶分法、桶內排序的來源、空桶照顯示的理由。
- 記錄圖表的無障礙要求（不靠顏色單獨辨識）。
- 記錄浪費統計的視窗，與清除鈕露出條件刻意不同步的理由。
- 記錄四種 row 操作的分工原則與確認規則。
- 記錄刪除確認期間該列必須留在清單上的要求與其成因。

**Non-Goals:**
- 無行為變更。
- 不涵蓋 `food-item` 的狀態演算法、`persistence` 的查詢、`advertising` 的版位行為、`notification` 的排程規則、`food-form-ui` 的表單。

## Decisions

### 統計與清單合併為單頁，移除獨立的分析分頁

原本的分析分頁與首頁共用同一批 active 食材，差別只在「分桶唯讀」與「平鋪可操作」。合併後統計移到頂部、清單改為分桶且可互動。理由：兩個分頁列出同一批資料，使用者需要在兩處之間切換才能「看到狀況」與「處理它」，而處理的動作本來就該發生在看到問題的當下。合併也讓 Tab 從三個減為兩個，降低整體導航複雜度。

### 分桶由 ViewModel 依效期狀態切分，桶內順序沿用查詢順序

active 清單取回後在 ViewModel 依 `ExpiryStatus` 濾成三桶。桶內不重新排序——`persistence` 已保證回傳依到期日升冪、同日再依建立時間升冪，濾出的子集合自然維持該順序。理由：排序是資料層契約（見 `persistence`），在 UI 層重排會讓同一份資料出現兩套排序邏輯。

### 空桶照樣顯示，header 標示數量

三個 Section 無論是否為空都渲染，header 顯示桶名與數量。理由：「已過期未處理：0 項」本身就是使用者最想確認的資訊；隱藏空桶會讓畫面在使用者表現最好的時候（沒有任何過期品）反而顯得最空洞，也讓「我到底有沒有過期的東西」需要靠桶不存在來推論。

### 圖表配 legend，不以顏色作為唯一辨識

現況甜甜圈右側放色點 + 桶名 + 數量的 legend。理由：色彩辨識障礙的使用者無法只靠紅／黃／綠區分三桶；legend 讓每個色塊都有文字對照。這與憲章的無障礙品質基準一致。中心顯示 active 總數，無 active 時顯示對應的空狀態文字。

### 浪費統計取近 30 天滾動視窗

浪費率的分子分母只計算 `resolvedAt` 落在近 30 天內的紀錄。理由：滾動視窗讓數字反映「最近的習慣」而非終身累計——終身累計會隨使用時間增長而愈來愈難改變，使用者改善了行為卻看不到數字動，失去回饋意義。舊資料自然滑出視窗，不需要任何清理作業。

浪費率定義為丟棄 /（吃掉 + 丟棄），無已處理紀錄時為未定義而非零，畫面顯示對應的空狀態文字而非「0%」——沒有資料與零浪費是不同的兩件事。

### 清除歷史鈕的露出條件是 all-time，不是 30 天視窗

統計看近 30 天，但清除鈕只要資料庫內存在任何已處理紀錄就露出。理由：若兩者同步，會出現這個邊界——使用者超過 30 天沒有處理任何食材時，統計區顯示「尚無已處理紀錄」且清除鈕不出現，但資料庫裡其實還留著更早的歷史，使用者沒有任何入口可以清除它。刻意不同步是為了讓「清除」永遠能清到實際存在的東西。

清除鈕放在浪費統計區的 header 而非設定頁，是就近原則：控制項與它影響的統計在同一區塊，使用者不需要推論「清除歷史」會清掉什麼。

### 四種 row 操作依「常用程度」分配到不同手勢，且不重複

向右滑為標記已使用、向左滑為刪除、單點整列進編輯、長按選單放延長效期與標記丟棄。理由：最常用的「吃掉了」給最順手的右滑；破壞性的刪除放在需要反向滑動的左側；較少用的延長與丟棄收進長按選單。選單若把四個操作全列一遍，會讓使用者無從判斷該用哪個手勢，也讓選單變長。

長按選單刻意不含刪除與編輯：破壞性操作與離開畫面的操作各自只保留一條路徑，避免誤觸與心智負擔。「標記已使用」則同時存在於右滑與選單中——原設計意圖是選單完全不重複其他手勢已提供的操作，實作上多留了這一項（見 Risks）。

代價是「長按能做什麼」不可見，因此在最後一桶的 Section footer 放一行提示說明三種手勢——這是 issue #2 針對發現性的修正。

### 只有刪除需要確認

標記已使用、標記丟棄、延長效期都直接執行，不跳確認。理由：這三者都留下紀錄或維持在清單中，誤觸的代價是可以再次操作修正的（誤標已使用可以重新新增；延長可以再改）。只有刪除是 hard delete、不留紀錄、無法復原，因此是唯一需要攔一道的操作。

### 刪除確認期間，該列必須留在清單上

刪除的滑動按鈕不使用 destructive role，只保留紅色外觀；實際刪除發生在確認之後。理由：SwiftUI 的 `swipeActions` 對標記為 destructive role 的按鈕會在點擊當下就把該列移出清單（它假設點擊即完成刪除）。但本畫面的刪除要先跳確認，於是會出現：列已從畫面消失、確認框才彈出、使用者選「取消」——資料還在但畫面上沒有，要等到下次重撈才回來。這是 issue #1 的實際缺陷。解法是放棄 role 帶來的自動行為，自行處理外觀與時機。

### 資料變動後重載並重排通知；進入畫面時重載

任何會改變 active 清單的操作（已使用、丟棄、刪除、延長）之後都重新查詢並觸發通知對帳；清除歷史只重載不重排（不影響 active）。畫面出現時亦重載。理由：本專案無自動觀察機制（見 `persistence`），清單必須明確重撈；而通知排程以當前 active 清單為準（見 `notification`），任何 active 變動都需要一次對帳。

## Implementation Contract

**Behavior (observable):**
- 首頁由上而下為：廣告位（釘頂）、現況圖表、浪費統計、三個分桶 Section、新增按鈕（釘底全寬）。
- 三個 Section 依「已過期未處理 → 3 天內到期 → 保存期限內」排列，即使某桶為空也顯示，header 帶數量。
- 圖表中心顯示 active 總數；沒有 active 食材時顯示空狀態文字。
- 浪費統計顯示近 30 天的浪費率與吃掉／丟棄筆數；沒有已處理紀錄時顯示空狀態文字而非 0%。
- 只要曾有任何已處理紀錄（不限 30 天內），浪費統計區的 header 就出現清除按鈕；點擊需確認。
- 向右滑一列標記已使用，該列立即離開清單，不跳確認。
- 向左滑一列出現紅色刪除鈕；點擊後彈出確認，**在使用者回答之前該列仍在清單上**；選取消則該列維持原狀。
- 長按一列出現選單，內含延長效期與標記丟棄，不含已使用與刪除。
- 單點一列進入編輯畫面。
- 延長效期彈出僅選新到期日的介面，選完即存並留在首頁。
- 最後一桶的 footer 顯示三種手勢的提示文字。
- 從編輯畫面返回後清單反映最新資料。

**Interface / data shape:**
- `HomeViewModel`：`@Observable @MainActor`；`doAction(_:)` 單一進入點，`Action` 分為 `view` 與 `dataResponse`。
- `State`：三個分桶陣列、`adsRemoved`、`pendingDeleteItem`、`extendingItem`、`consumedCount`、`wastedCount`、`hasHistory`、`showClearHistoryConfirm`；計算屬性 `items`（三桶串接，急→緩）、`activeTotal`、`resolvedTotal`、`isEmpty`、`wasteRate`（無資料時為 nil）。
- `Router`：`toAdd` / `toEdit(FoodItem)`。
- `wasteWindowDays` 為具名常數。
- `FoodRowView`：跨畫面共用的純展示列（縮圖／名稱／到期文字／狀態色點），本身不含互動；互動由使用它的畫面於外層包上。

**Acceptance criteria:**
- 三個 Section 在對應陣列為空時仍渲染。
- `wasteRate` 在 `resolvedTotal` 為 0 時回傳 nil。
- `hasHistory` 由未經 30 天過濾的已處理集合是否為空決定。
- 刪除的 swipe 按鈕未使用 destructive role。
- 標記已使用／丟棄／刪除／延長之後皆呼叫重載與通知對帳；清除歷史只呼叫重載。
- `FoodRowView` 內不含任何 swipe、context menu 或點擊處理。

**Scope boundaries:**
- In scope：版面組成、分桶與空桶、圖表與 legend、浪費統計視窗與清除條件、四種操作與確認規則、確認期間的列存續、重載與對帳時機、空狀態。
- Out of scope：效期演算法與出口語意（`food-item`）、查詢與排序與圖片剝離（`persistence`）、廣告版位行為（`advertising`）、通知排程規則（`notification`）、表單畫面（`food-form-ui`）、導航機制（`navigation`）。

## Risks / Trade-offs

- [長按選單重複了「標記已使用」，與其設計意圖不符] → `HomeView` 的 `contextMenu` 註解與 `specs/03-screens/home.md` 皆宣稱「長按只放滑動／點擊之外的動作」，但實作中選單同時包含右滑已提供的「標記已使用」。本 baseline 依現況記錄（選單含三項）。這個重複本身可能是合理的——長按不需要精確的滑動手勢，對操作精準度有困難的使用者是更可靠的替代路徑——但目前沒有任何地方把它記載為刻意決定。若要對齊，應是獨立 change：移除選單中的該項，或把「提供無滑動替代路徑」明確寫成設計意圖。
- [長按選單的存在依賴 footer 提示] → 提示只出現在最後一桶的 footer，使用者若不捲到底就看不到；延長效期與標記丟棄因此可能長期未被發現。這是 issue #2 之後的現況，並非完全解決。
- [誤觸右滑「已使用」沒有復原入口] → 該列立即離開清單且不跳確認，使用者只能重新新增一筆。以誤觸成本低於每次都確認的干擾為前提，但確實無 undo。
- [浪費率的 30 天視窗與清除鈕的 all-time 條件不一致] → 使用者可能看到「尚無已處理紀錄」卻仍有清除按鈕，兩者傳達的訊息表面矛盾。這是刻意的取捨（見 Decisions），但畫面上沒有任何說明。
- [統計與清單共用單頁] → 食材數量成長後，使用者每次進首頁都要捲過統計區才看到清單。目前沒有收合或跳過的機制。
- [刪除按鈕放棄 destructive role] → 失去系統對破壞性操作的預設語意（包含未來可能的無障礙提示）。以正確的確認流程優先。
