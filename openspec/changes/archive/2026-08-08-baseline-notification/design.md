## Context

到期通知是這個 app 的核心價值——沒有提醒，它就只是一份手動維護的清單。但通知的排程狀態存在系統裡、不在 app 的資料庫裡，因此 app 的資料與系統的待發通知隨時可能不一致：使用者可能在通知已排好之後改了到期日、把食材標記為已使用、或直接刪除。

處理這種不一致有兩種路線：逐筆追蹤（每個資料操作都配對一個排程操作），或整批對帳（每次都以當前資料重建全部排程）。v1.0.0 選了後者。

## Goals / Non-Goals

**Goals:**
- 記錄「清空重建」對帳策略取代逐筆增刪的理由。
- 記錄 iOS 64 則上限的處置方式與其可見後果。
- 記錄排程時機（到期當天 09:00）與單位（每項一則）。
- 記錄權限請求的情境式時機與三種狀態的分流。
- 記錄 DEBUG 即時觸發模式必須留在 `#if DEBUG` 內。

**Non-Goals:**
- 無行為變更。
- 不涵蓋 `navigation` 的路由實作、`settings-ui` 的版面、`food-item` 的效期判定。

## Decisions

### 以「清空重建」對帳，而非逐筆排程與取消

`reconcile(activeFoods:)` 先 `removeAllPendingNotificationRequests()`，再依當前 active 清單重建。所有資料變動路徑——新增、編輯、延長、標記已使用、標記丟棄、刪除——都只需要呼叫這一個方法。理由：逐筆維護需要為六種資料操作各自配對正確的排程動作，而其中任何一條路徑漏改都會留下幽靈通知（食材已經吃掉了卻還在提醒），這種錯誤在測試中極難發現，因為它要等到未來某天才會顯現。整批重建讓「排程 / 取消 / 重排」退化成同一個操作，正確性只依賴一個函式。代價是每次都要重寫全部待發通知，但以此 app 的資料量（上限 60 則）成本可忽略。

### 待發上限取 60，低於 iOS 的 64

`maxScheduled = 60`。理由：iOS 對每個 app 的待發通知數有 64 則硬上限，超過的部分是**靜默丟棄**——沒有錯誤、沒有回報。留 4 則 headroom 是為了避免恰好卡在邊界時行為變得不可預測。取捨的順序是「最近到期優先」：先濾掉已經無法觸發的（見下），再依觸發時間升冪取前 60。理由：使用者最需要的是即將到期的提醒；較遠期的項目在時間推進、近期項目被消化之後，會在下一次對帳時自然進入排程範圍。

### 觸發時間已過的項目不排程

排程前先濾掉 `fireDate <= now` 的項目。理由：`UNCalendarNotificationTrigger` 對過去的時間點不會觸發，排了也只是佔用 64 則額度中的一格。典型情境是使用者在下午才記錄一筆「今天到期」的食材——當天 09:00 已過，這筆不排程。

### 每項食材一則，以食材 id 為通知 identifier

不做「每天彙整一則」。理由：一對一讓通知內容可以直接寫出食材名稱（「『菠菜』今天到期」），比彙整訊息更能促成行動；以食材 `id` 為 identifier 則讓同一筆食材永遠對應同一則通知，重複排程會覆蓋而非疊加。代價是同一天多項到期會收到多則通知，且吃掉更多的 64 則額度——這是量大時的既定優化方向。

### 權限在使用者第一次儲存食材時才請求

不在啟動時、也不在 Onboarding 請求通知權限，而是等到使用者第一次按下儲存。理由：此時使用者剛剛表達「我要記住這項食材」，通知權限的用途在當下是自明的，同意率遠高於一個沒有脈絡的啟動彈窗。而 iOS 的權限彈窗只會出現一次——被拒絕後就只能引導使用者去系統設定，因此這一次機會必須用在最有說服力的時機。

### 只在尚未決定時彈窗，已決定則導向系統設定

`requestAuthorizationIfNeeded()` 先查狀態，只有 `notDetermined` 才呼叫 `requestAuthorization`。設定畫面的通知列同樣分流：未決定 → 直接請求；已授權或已拒絕 → 導向系統設定。理由：對已經拒絕的使用者重複呼叫 `requestAuthorization` 不會再顯示彈窗（系統直接回傳拒絕），若 UI 表現得像「按了沒反應」，使用者會以為 app 壞了。明確導向系統設定才是唯一能改變狀態的路徑。

`provisional` 與 `ephemeral` 一併視為已授權——它們都能送達通知。

### 通知 payload 帶 deeplink，缺漏時回退首頁

內容的 `userInfo` 帶 `{"deeplink": "foodentropy://home"}`。接收端在 payload 缺漏時回退到首頁（見 `navigation`）。理由：payload 是跨版本的資料——舊版本排好的通知可能在新版本安裝後才觸發。明確的回退讓這種情況不會變成「點了沒反應」。

### DEBUG 專用的即時觸發模式必須留在編譯條件內

`immediateTestFire` 在 DEBUG 下改用 10 秒的間隔觸發，且不濾掉已過期項目；Release 一律走正式的 09:00 日曆觸發。此模式僅在資料變動時使用，前景對帳一律走正式行為。理由：到期通知在正常情況下要等到隔天早上才能驗證，沒有即時模式就無法測試。但它若進了 Release，使用者每次新增食材都會在 10 秒後被通知——而且是連同已過期項目一起。與 `app-shell` 記錄的環境開關同屬一類，必須以 `#if DEBUG` 編譯期排除。前景對帳刻意不使用此模式，否則「只是開啟 app」就會觸發一輪通知。

### 服務可注入為停用狀態以供測試

`init(active:)` 傳入 `false` 時所有方法都是 no-op。理由：單元測試不應該真的去動系統的通知中心——那會污染開發機的通知狀態，且在 CI 環境沒有可用的通知授權。

## Implementation Contract

**Behavior (observable):**
- 新增一筆到期日在未來的食材，該食材到期當天早上 09:00 收到一則寫著食材名稱的通知。
- 把某筆食材標記為已使用後，該筆原本的到期通知不再送達。
- 修改某筆食材的到期日後，提醒改在新的到期日送達，舊日期不再送達。
- 在下午新增一筆今天到期的食材，不會收到當天的通知。
- 第一次儲存食材時出現系統通知權限彈窗；之後儲存不再出現。
- 曾拒絕通知權限的使用者，在設定點擊通知列會被帶往系統設定。
- app 在前景時到期通知仍以橫幅顯示。
- 點擊通知開啟 app 並停在首頁。

**Interface / data shape:**
- `NotificationAuthStatus`：`authorized` / `denied` / `notDetermined`。
- `NotificationService`：`@MainActor`、`static let shared`、`init(active: Bool = true)`。
- `authorizationStatus() async -> NotificationAuthStatus`；`requestAuthorizationIfNeeded() async -> NotificationAuthStatus`（`@discardableResult`）。
- `reconcile(activeFoods: [FoodItem], immediateTestFire: Bool = false) async`。
- 常數：觸發時刻為 9 時整；待發上限為 60。
- 通知 identifier 為食材 `id` 的字串形式；`userInfo` 帶 `deeplink` 鍵。
- 通知標題與內文皆取自 String Catalog。

**Acceptance criteria:**
- `reconcile` 的第一個動作是移除全部待發通知。
- 排程集合經過「濾掉觸發時間已過者 → 依觸發時間升冪 → 取前 60」三步。
- `immediateTestFire` 造成的行為差異全部位於 `#if DEBUG` 區塊內。
- `requestAuthorization` 僅在狀態為 `notDetermined` 時被呼叫。
- 通知內容字串以 `String(localized:)` 取得，無硬編。

**Scope boundaries:**
- In scope：排程時機與單位、對帳策略、上限處置、過期濾除、權限時機與分流、payload 慣例、前景呈現、DEBUG 隔離、測試停用注入。
- Out of scope：點擊後的路由（`navigation`）、設定列版面與被拒文案（`settings-ui`）、效期狀態判定（`food-item`）、自訂提醒時機（v1.0.0 不提供）。

## Risks / Trade-offs

- [超過 60 項 active 食材時，較遠期的項目沒有提醒] → 使用者不會收到任何「有項目未被提醒」的訊息，只會在某天發現某項食材過期了卻沒被提醒。以此 app 的個人使用規模罕見，但一旦發生是靜默的。
- [每項一則會加速觸及 64 則上限] → 同一天多項到期時會連續收到多則通知，體感吵雜，也更快耗盡額度。「每天彙整一則」是既定的優化方向，但會犧牲「通知裡直接看到食材名稱」這個促成行動的優點。
- [排程狀態不在 app 資料庫內] → 對帳只在資料變動與進入前景時發生。若使用者長期不開 app，排程停留在最後一次對帳的結果；期間新到期的項目仍會依當時排定的內容送達，但若清單早已改變，內容可能與現況不符。
- [`removeAllPendingNotificationRequests` 會清掉所有待發通知] → 目前 app 只使用到期通知一種，若未來新增其他類型的本地通知，這個對帳會連同它們一起清除。屆時需要改以 identifier 前綴區分。
